# Fact Knowledge Layer

Extracts checkable claims from PDFs, proves every claim against its source text,
and decides whether claims from different documents corroborate each other,
contradict each other, or only appear to conflict because they measure different
things.

**The core engine is deterministic and runs with no API key.** No LLM is
involved in reading a PDF, extracting a claim, or deciding a relationship. An
LLM can optionally be switched on to adjudicate the small number of pairs the
rules explicitly mark ambiguous. Setting `FKL_STRICT_DETERMINISTIC=1` refuses
every code path that would touch a provider — the extractor factory rejects
`llm` and `hybrid`, and relationship building never imports the client. The
`TestNoLLMInDecisions` suite pins this in tests.

Nothing in the pipeline is specific to a document, a company, or a metric.

**The four required cases, as real system output:
[`samples/REQUIRED_CASES.md`](samples/REQUIRED_CASES.md).** That file is
generated by `scripts/export_samples.py` from the ingested corpus — every quote
in it was located programmatically in the source PDF, and every example is
picked by rule rather than by hand. Every claim in the UI can be shown in the
source PDF with its bbox drawn on the page (server-rendered by PyMuPDF, no
browser-side PDF renderer needed).

## 1. Setup and Run Instructions

### Requirements

- Python 3.11 or 3.12 (3.13+ lacks wheels for some dependencies)
- No API key, no database server, no network access

### Install

```bash
git clone <your-repo-url> && cd fact-knowledge-layer
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

### Quickstart (about 20 seconds)

For reviewers who want to see the system work without waiting on the full
corpus:

```bash
./scripts/quickstart.sh
```

Ingests one small PDF plus one bigger one (about 20 s combined), then boots
the UI at <http://127.0.0.1:8000>. Enough claims and cross-document
relationships land in the store to demonstrate every verdict type.

### Run the UI

```bash
.venv/bin/python scripts/serve.py
```

Open <http://127.0.0.1:8000> and drop a PDF anywhere on the page. Ingest runs
as a background job, with the progress bar following the pipeline through
extraction, grounding and comparison.

**Relationships** is the view worth opening first. Each verdict is one card
laying the two claims side by side in a single grid — value, then a row per
context field — with the rows that disagree banded, so what differs is visible
before anything is read. Under that sit the explanation, an expandable
step-by-step reasoning trace, and the counterfactuals. Each side's evidence row
has a "View in source PDF" toggle that renders the exact region of the exact
page with its bbox drawn on top.

**Claims** and **Needs review** are lists rather than cards, one line per fact,
with the evidence, scores and source page one click away.

### Run from the command line

```bash
# ingest PDFs, then build cross-document relationships
.venv/bin/python scripts/ingest.py starter-datasets/delhivery/*.pdf

# the whole starter corpus (6 PDFs, 511 pages) -- about 90 seconds
.venv/bin/python scripts/ingest.py starter-datasets/*/*.pdf

# only the first N pages of each file, for a quick look
.venv/bin/python scripts/ingest.py --max-pages 16 some.pdf
```

Re-running the same file is a no-op: documents are content-addressed, so an
already-completed PDF is skipped. Use `--force` to redo it.

### Run the tests

```bash
.venv/bin/python -m pytest                          # unit tests (fast)
.venv/bin/python -m pytest -m integration           # end-to-end (~100s)
.venv/bin/python -m pytest -m ""                    # everything
```

The unit suite runs offline and covers the required cases through crafted
input dictionaries (corroboration across units, contradiction in percentage
points, standalone-vs-consolidated reconciliation, fiscal-year and unit
equivalence, predicate and subject false positives, partial coverage,
grounding failure, missing context, provenance, table reconstruction,
checkpoint/resume, cross-corpus generalisation, contradiction preconditions
and entity/predicate specificity).

The integration suite in `tests/test_required_cases.py` re-ingests three real
PDFs from the starter corpus, then asserts that the live store actually
contains one relationship of each required kind, that both claims carry real
evidence, that each verdict was decided by `"rules"` (never the LLM), and
that at least one extraction failure was surfaced through the grounding
guards. It is the acceptance test for the assignment: if it passes, every
promise in this README is checkable against the live pipeline.

### Benchmark

```bash
.venv/bin/python scripts/benchmark.py --modes deterministic --pages 0
```

### Optional: enable the LLM fallback

Everything above works without this. To let the model adjudicate ambiguous
pairs only:

```bash
cp .env.example .env          # then add your key
export FKL_ENABLE_LLM_FALLBACK=1
.venv/bin/python scripts/ingest.py --escalate some.pdf
```

`.env` is gitignored. The default configuration targets Groq, but the provider
is three settings (`FKL_LLM_BASE_URL`, `FKL_LLM_API_KEY_ENV`, `FKL_LLM_MODEL`),
so any OpenAI-compatible endpoint works.

## 3. Approach

### Architecture

```
                      PDF
                       │
            ┌──────────▼───────────┐
            │ PyMuPDF / pdfplumber │   text, words, coordinates,
            │  structured pages    │   headings, captions, tables
            └──────────┬───────────┘
                       │
            ┌──────────▼───────────┐
            │  Rule-based claim    │   sentence rules + table
            │     extraction       │   reconstruction
            └──────────┬───────────┘
                       │
            ┌──────────▼───────────┐
            │ Grounding +          │   locate the evidence for real,
            │ claim normalisation  │   quarantine what cannot be located
            └──────────┬───────────┘
                       │
            ┌──────────▼───────────┐
            │ Entity matching      │   two independent gates
            │ Predicate matching   │
            └──────────┬───────────┘
                       │
            ┌──────────▼───────────┐
            │ Context comparison   │   period / unit / scope / basis /
            │                      │   denominator / modality
            └──────────┬───────────┘
                       │
   ┌───────────┬───────┼────────┬───────────────┬───────────────┬─────────────┐
   ▼           ▼       ▼        ▼               ▼               ▼             ▼
CORROB.  CONTRADICT. RECONCILED SUPERSEDES  COMPONENT_OF   PARTIAL_COVER UNDERSPECIFIED
                                              _TOTAL                          │
                                                                    ambiguous only, opt-in
                                                                              ▼
                                                                      Optional LLM
```

The eighth verdict, `component_of_total`, was added when the pairwise partial-
coverage rule was refined: if the narrower claim is 5 %–100 % of the broader
one, the pair is a plausible component. A corpus-wide post-pass then groups
these by broader claim and checks whether the siblings sum to the broader
value within 5 %. Confirmed groups have their trace and explanation extended
with the arithmetic. This is the "component-of-total math" the earlier design
listed as a next step; it lands as pairwise labelling plus a deterministic
post-pass rather than a graph traversal.

### The central decision: extract claims, not facts

A "fact" flattened to a value cannot be compared safely. `8,142` and `2,076`
look like a contradiction until you know one is a full year and the other a
quarter. So the unit of extraction is a **claim**, which carries the context
that makes it comparable:

```json
{
  "subject": "Delhivery Limited",
  "predicate": "revenue from customers",
  "value": "8,142",
  "value_num": 81420000000.0,
  "unit": "INR crore",
  "context": {
    "period": "FY24", "scope": null, "basis": null,
    "geography": null, "as_of": null, "denominator": null
  },
  "modality": "reported",
  "evidence": {
    "page": 14, "text": "Revenue from customers(1) | FY24 | 8,142",
    "char_span": [1183, 1208], "bbox": [138.6, 170.8, 472.5, 184.2]
  },
  "confidence": { "extraction": 0.88, "grounding": 1.0 }
}
```

A null context field means *the document did not say*, which is not the same as
the two claims disagreeing. **Missing context can never, on its own, produce a
contradiction.**

### Why deterministic

The previous version of this system sent PDF chunks to an LLM and asked for
facts. Replacing that with rules was not about avoiding AI — it was driven by
three measured problems:

1. **It could not be trusted.** The model reconstructed a bar chart's *visual*
   layout into a quote (`"Cross Border Services revenue 109 153 174 Q4 FY23…"`)
   whose numbers were real but whose text never appeared in the document.
2. **It was unverifiable.** Structure that is recoverable — a row label, a
   column header, a corner cell declaring `₹ Cr` — was being guessed at rather
   than read.
3. **It was slow and rate-limited.** The full corpus was a 3-hour job against a
   free-tier token budget, and could not run at all without a key.

Where the evidence is structurally recoverable, reading it is better than
asking a model to guess it. The LLM is reserved for genuine ambiguity.

### Deterministic PDF understanding

Pages are rebuilt from PyMuPDF's structured dictionary rather than flat text, so
**every character offset maps to a line and therefore to a bounding box**. That
is what lets a grounded claim carry real coordinates. Headings are detected
typographically (relative font size and weight), and text repeated across many
pages is classified as page furniture and excluded — a structural rule that
never needs to know what the boilerplate says.

**Table reconstruction** runs three strategies and scores them:

1. **PyMuPDF ruled lines** — fast and excellent on real grid tables, but returns
   near-empty boxes on chart-heavy slides and merges rows on some appendices.
2. **pdfplumber text alignment** — recovers row structure where ruling lines
   are absent.
3. **Coordinate clustering** — builds a grid from word positions alone: rows by
   clustering on vertical centre, columns by finding the vertical whitespace
   that almost no row crosses. Wide statistical tables defeat both other
   strategies, which over-segment them into a sparse grid where most cells are
   empty; the words themselves still carry the structure.

Each candidate is scored on structural quality only — cell fill rate, whether a
header row and label column exist, how many cells are numeric, and whether cells
show signs of having been merged. Overlapping candidates are deduplicated and
the best kept. Multi-row headers are merged into one header per column, the row
that names the periods is preferred as the column header over a spanning title,
and units are inherited from the corner cell, caption or header.

A table is found as a *band* of consecutive rows carrying several figures, and
columns are derived from the words in that band alone. Doing it the other way
round — deriving columns from the whole page — reads a two-column article
layout as a two-column table, because the gutter between text columns looks
exactly like a column separator.

Result: **430 usable tables across 511 pages**, producing 4,131 structured
claims, with chart slides, prose columns and catastrophically-merged tables
correctly rejected so those pages fall back to sentence extraction.

### Rule-based claim extraction

Two paths. **Sentence claims** match a label, a linking phrase and a value that
are contiguous in the page text (`"Core inflation increased to 4.6 percent"`);
because they are contiguous, the evidence span is exact. **Table claims**
recombine a row label, a column header and a cell into one claim, inheriting
period from the column header when it parses as one, and unit from the corner
cell or caption.

The vocabulary these rules use lives in `fkl/lexicon.py`, isolated so it is
auditable that it is ordinary English reporting language — linking verbs, scope
and basis qualifiers, modality words, attribution patterns — and not domain
knowledge. The test for whether a term belongs there: *would it be equally true
of a medical trial report, a municipal budget, and a football annual?*

Change verbs are handled separately from level verbs, because "revenue
increased by 578" and "revenue was 578" are different assertions; collapsing
them would manufacture contradictions.

### Grounding, and what gets quarantined

Nothing an extractor asserts is trusted. Deterministic sentence claims record
the character range they were cut from, so verification is an equality check.
Table claims verify the row label and the cell value on the page independently.
Claims that merely *quote* (an LLM, or a fallback path) are located by exact
then fuzzy search.

The fuzzy path had a real weakness worth describing, because finding it changed
the design. `partial_ratio` rewards the best-matching sub-window, and character
similarity cannot see reordering — so text rebuilt out of a chart still scored
0.80–0.85, above the acceptance threshold. Scoring is now scaled by how much of
the quote's **word order** survives in the located window (a typo-tolerant
longest-common-subsequence over tokens). Measured:

| quote | score | outcome |
|---|---|---|
| verbatim | 1.00 | accepted |
| verbatim with a typo | 0.98 | accepted |
| chart labels and values reordered | 0.71 | quarantined |
| labels then values, chart style | 0.60 | quarantined |
| stitched from non-adjacent lines | 0.31 | quarantined |
| wholly fabricated | 0.00 | quarantined |

A quarantined claim is stored and visible but **never enters comparison**. A
relationship must not rest on evidence we could not verify.

### Two independent gates

Identity is settled before values are looked at.

**Entity matching** is deterministic: unicode folding, legal-suffix removal,
containment, and acronym expansion (`RBI` = `Reserve Bank of India`, `IMF` =
`International Monetary Fund`) — while refusing `Delhivery` = `DHL`, which
share letters but no content words.

Choosing *which* entity a document is about happens once per document, by
frequency and page-spread, with one correction: a phrase that almost always
arrives with a definite article is a description rather than a name. "The
Reserve Bank", "the Union Budget", "the Executive Board" are roles, documents
and organs; `Delhivery` and `India` are names. This is what stops a first-party
report being attributed to its own publisher instead of its subject — see
section 4, where it is the difference between finding a contradiction and
finding none.

**Predicate matching** returns three outcomes, not two, because `revenue` and
`revenue from operations` are neither identical nor unrelated:

- `same` → compare the values
- `related` → same family, different measure; can never be a contradiction
- `different` → never compared at all

Two rules keep `same` honest, both added after they produced false
contradictions on the starter corpus. A **symmetric difference** in content
words blocks `same` however high the string overlap: `Credit-Deposit Ratio` and
`Credit-GDP Ratio` score 0.70 on `token_sort_ratio` but name different
denominators. And a single added word that is *itself a kind of measurement* —
a ratio, a deficit, a growth rate — yields `related`, not `same`: a revenue
deficit is a different quantity from revenue.

This is where an earlier design failed hard. Retrieval used a single embedding
over `(subject, predicate)`; when two claims share a subject, the subject
dominates the vector, so `headcount` and `total revenue` scored 0.765 against
each other — about the same as genuine synonyms — and were reported as a
confident contradiction. Blocking on the two fields separately removes the
failure mode and needs no model at all.

### Context-aware comparison

Comparison runs `entity → predicate → context → values → verdict`, and every
verdict is produced by a rule that actually fired. The trace records them in
order; it is not narration written after the fact.

```
entity gate: matched -- identical after normalisation ('delhivery')
predicate gate: same -- one predicate adds a single qualifier ('balance')
period: same -- neither claim states a period
unit: same -- different scale ('INR crore' vs 'INR million'); normalised
scope: same -- neither claim states a scope
value: equivalent -- values agree within 0.5% (5.444e+10 vs 5.44387e+10)
decision: comparable context + agreeing values -> corroboration
```

Eight outcomes, because forcing everything into three produces false
contradictions: `corroboration`, `contradiction`, `reconciled`, `supersedes`
(an estimate revised by a later actual), `component_of_total` (a plausible
share, upgraded to *confirmed* when siblings sum to the parent),
`partial_cover` (related but no numeric check applied), `underspecified`,
`unrelated`.

`contradiction` is the only accusatory verdict, so it carries extra
preconditions. Two of them are about knowing what the numbers even are:

- **A unit stated on one side only is `unknown`, not `same`.** `US$3.9
  trillion` against a bare cell `9.2` is not a crore-versus-million difference
  that normalisation can absorb.
- **Two unitless table cells cannot contradict each other** unless the row
  label names a rate. A row label is only meaningful relative to its table:
  "Deposits" is per-cent growth in one document and a share of GDP in another.
  Sentence claims are exempt — their predicate arrives with the sentence that
  qualified it.

Normalisation is general-language: magnitudes (thousand/lakh/million/crore/
billion), currencies, percentages, and periods (`FY24` = `FY2024` =
`fiscal year 2023-24`; `2024-25` = `FY25`; a quarter is not its year; a month
is not a fiscal year). **Rates are compared in percentage points, not
relatively** — a relative tolerance would call 4.0% and 2.8% a "30% difference"
and hide that they are two incompatible reported rates.

### Spanning column groups

The RBI's Appendix Table 4 puts two column groups under three identical year
headers, so the row `Credit-Deposit Ratio` produces six cells and three of
them are labelled `2023-24`. Left alone, those three become claims about the
same period with different values, and they are then compared as
alternatives — one produces the corroboration finding, one produces the
contradiction, but they were never meant to be alternatives.

`fkl/tables.py::_column_groups` catches this the moment it sees a period
label repeated in the primary header row. It walks the header rows *above*
the period row, forward-fills their labels across empty cells (which is how
spanning cells arrive from every extractor), and gives each column its own
group label. The label is folded into `ctx.scope` when the table claim is
built, so the two 2023-24 columns get distinct scopes and stop being
compared as though they were one measurement.

### Semantic (status) claims

The brief mentions the case explicitly: *"a director may appear active in
one document and resigned in a later one"*. That is a semantic claim about
an entity's state — different in kind from a numeric fact, and worth its own
extraction path.

`fkl/extract_rules.py::status_claims` matches a proper-noun subject, an
explicit state-change verb from `STATUS_VERBS` (resigned, appointed, joined,
retired, relocated, merged, acquired, discontinued, ...), an optional role
target, and an optional effective date. The subject must be a name the
document already uses; verbs of general activity ("said", "reported") never
fire this path. Comparison is likewise a separate branch: two agreeing
statuses corroborate, two conflicting statuses supersede when the periods
can be ordered, and contradict when they cannot.

### Rule IDs, not just verdict names

Every branch in the cascade carries a stable identifier (`R00`, `R01`, ...,
`R70`, `R99`). The identifier is stored on the relation and shown in the UI
next to "Deterministic rules". Two relations with the same rule id were
decided by the same code path, and a rule change produces a clean diff via
`scripts/replay.py` — it re-runs every stored pair through the current
cascade and prints only the transitions. The verdict `kind` is the label a
reader sees; the `rule_id` is what a maintainer diffs against.

### Precision-derived tolerance

Rather than a flat 0.5 % relative tolerance, the value comparator derives its
tolerance from the coarser side's least significant digit. `₹8,142 crore` is
written to the nearest whole crore, so its precision is ±0.5 Cr — about
±5,000,000 in normalised units — and any real difference below that is at
the limit of what the document actually asserts. `₹81,415.38 million` is
written to two decimals, precision ±0.005 Mn. The comparator uses the
coarser of the two.

The measurable effect on the starter corpus: **corroborations went from 28
to 40** as pairs that previously landed in `reconciled` (values differ, but
within rounding) now cleanly resolve to `corroboration` with a trace that
names the precision. The two contradictions survive unchanged because 78.1
vs 80.3 (both to one decimal, precision ±0.05) disagree by 2.2, which is
44 × their precision.

### Counterfactuals

The API answers, for any relation, *what would change the verdict?* — by
re-running the cascade with one qualifier ablated at a time. In the UI, an
expandable "What would change this?" section on each card fetches
`GET /api/relations/{id}/counterfactuals` and lists only the ablations
that actually change the outcome. On the credit-deposit contradiction it
returns exactly one:

> If **period** were missing on both sides → verdict would be
> **underspecified** (rule R60): "the values differ, but period is stated
> by only one document."

Which is the honest reading. The period is the one qualifier doing work on
that pair; every other stated context supports the same conclusion. No new
logic runs in the counterfactual — the same cascade decides both the live
verdict and the ablated one, so this cannot drift from the real answer.

### Confidence is four numbers, not one

Extraction, grounding, matching and relationship confidence answer different
questions. A verdict is bounded by the weaker of the two claims, so a shaky
extraction cannot become a confident contradiction just because two numbers
differ. This is pinned by a test.

Both contradictions are real: the RBI's Combined credit-deposit ratio disagrees
with the IMF's Financial Soundness Indicator by 2.7 % in 2023-24 and 2.1 % in
2024-25. In 2022-23 the same pair corroborates, so the system is not just
producing a single stuck finding across three years — it distinguishes the
years where the aggregates agree from the years where they do not. The
sub-population rows (`Urban`, `Rural`) sit under the RBI's spanning column
group and land in `underspecified` when compared to the IMF, because the IMF
does not state which population it covers. That is the correct answer.

Of the 1,599 pairwise `component_of_total` labels, 33 groups are confirmed by
the corpus-wide post-pass — the siblings actually sum to the broader value
within 5 %. The rest are plausible components that the post-pass could not
confirm from the numbers alone.

Against the LLM-based pipeline it replaced, on the same machine and corpus:

| | deterministic | LLM-based |
|---|---|---|
| full corpus (511 pages) | **98 s** | ~3 hours (rate-limited, never completed) |
| Q4 deck (27 pages) | **1.4 s**, 519 claims | minutes, 43 claims from 12 pages |
| API calls | **0** | ~163 |
| runs without a key | **yes** | no |

The LLM comparison could not be completed at full scale: the free tier caps at
8,000 tokens/minute, and a corpus-wide run exhausted the budget without
finishing. The deterministic path processes the whole corpus in under two
minutes on a laptop with no account.

At small scale the LLM path does run, and `samples/BENCHMARK.md` measures all
three modes on the same 8 pages:

| | deterministic | hybrid | llm |
|---|---|---|---|
| claims extracted | 13 | 46 | 44 |
| LLM calls | **0** | 2 | 1 |
| runtime | **0.5 s** | 7.6 s | 73.5 s |

The LLM extracts more claims than the rules do on those pages — that is a real
advantage and worth stating plainly — at roughly **150x the wall time** and
with a dependency on someone's API budget. The hybrid column is the
architecture's answer: rules first, model only on pages the rules could not
read, which recovers most of the recall for a fraction of the calls. What none
of the three columns shows is a relationship, because eight pages of one
document give nothing to compare across.

## 4. Limitations and Next Steps

These are the things that genuinely do not work. Measurements and diagnoses,
not disclaimers.

### The contradiction the corpus does contain, and what it cost to find it

The system now reports **2 contradictions** across the six starter PDFs and
both are real. Same finding, two consecutive fiscal years:

| claim | source | value | period |
|---|---|---|---|
| `Credit-Deposit Ratio` (`Combined` column group) | RBI Annual Report, Appendix Table 4, p95 | **78.1** | 2023-24 |
| `Credit-to-deposit ratio` | IMF Article IV, Table 7 (Financial Soundness Indicators), p50 | **80.3** | 2023/24 |
| `Credit-Deposit Ratio` (`Combined` column group) | RBI Annual Report, Appendix Table 4, p95 | **79.1** | 2024-25 |
| `Credit-to-deposit ratio` | IMF Article IV, Table 7 | **80.8** | 2024/25 |

Same country, same named banking ratio, same fiscal year, both dimensionless,
and the numbers do not agree by 2 %+. The RBI publishes three column groups
(`Urban`, `Rural`, `Combined`); the `Combined` column is the all-banks
aggregate, which is exactly what the IMF's Financial Soundness Indicator is
implicitly measuring. Everywhere else the RBI table has a sub-population
(Urban, Rural), that pair against the IMF's unqualified figure is correctly
`underspecified` rather than a contradiction — the sub-population is not
directly comparable to the aggregate. In 2022-23 the same pair *corroborates*
(75.8 = 75.8), so the system does not report a fixed finding: it reports the
years in which the aggregates agree and the years in which they do not.

Getting from the previous **10 contradictions** to these **2 real ones**
required fixing six defects, in this order. Each was found by reading real
output rather than by reasoning about the design.

**1. Entity detection elected the publisher, not the topic.** The RBI Annual
Report was attributed to `Reserve Bank`, so its claims never met the Economic
Survey's or the IMF's claims about `India` at the entity gate. The fix is a
property of English rather than of these PDFs: proper names of companies and
countries take no article — "Delhivery reported", "India's exports" — while
roles, organs, instruments and *institutions referring to themselves* do. In
its own annual report the RBI writes "the Reserve Bank conducted", "the Reserve
Bank revised", because inside its own report the author needs no introduction.
Measured across all six documents, the ratio separates cleanly:

| candidate | document | occurrences | with "the" |
|---|---|---|---|
| Reserve Bank | RBI Annual Report | 21 | 20 (**0.95**) |
| India | RBI Annual Report | 19 | 0 (0.00) |
| Delhivery | Delhivery AR | 31 | 1 (0.03) |
| India | IMF Article IV | 34 | 0 (0.00) |

A phrase that arrives with a definite article at least 60% of the time (over at
least four mentions) is demoted. Entity detection went from four of six
documents correct to **five of six**.

**2. The longest-form rule promoted `India` to `Indian`.** A separate bug,
exposed by the first fix: the step that prefers "Delhivery" → "Delhivery
Limited" only checked string prefix, so "India" was replaced by the more
frequent "Indian". It now requires the longer form to extend the shorter one by
whole words.

**3. Comparisons were asserted across unknown units.** `US$3.9 trillion` was
compared against a bare table cell `9.2` and the eleven-order-of-magnitude gap
was written off as a crore-versus-million scale difference. A unit stated on
one side only is now `unknown`, not `same`, and an unknown unit blocks a
contradiction the same way a one-sided period does.

**4. A table row label is not a predicate.** The largest source of false
contradictions was two unitless table cells whose row labels read alike:
"Deposits" in the RBI's money-and-credit table is year-on-year growth in per
cent; "Deposits" in the IMF's fiscal table is a balance as a share of GDP. The
labels match, the periods line up, the numbers disagree — and they were never
the same measurement. Two unitless *table* claims whose row label does not name
a rate are now `underspecified`. Sentence claims are exempt, because their
predicate arrives with the sentence that qualified it.

Two predicate-gate fixes fell out of the same investigation. `token_sort_ratio`
scored "Credit-Deposit Ratio" against "Credit-GDP Ratio" at 0.70 — enough to be
called one property, though `deposit` and `gdp` are different denominators; a
symmetric difference in content words now blocks a `same` verdict unless the
leftovers are spellings of one word ("operation" / "operating"). And "revenue"
against "revenue deficit" was treated as one predicate adding a qualifier to
another, when a deficit is a different quantity from the thing it is a deficit
in; a single added word that is itself a kind of measurement now yields
`related`.

Two more fixes landed after the earlier work, on the way from ten down to two:

**5. Spanning column headers were flattened away.** The RBI's Appendix Table 4
puts two column groups under the same three year headers, so the row
`Credit-Deposit Ratio` produced six cells and three of them were labelled
`2023-24`. Left alone, those three become claims about the same period with
different values, and the system compared them as alternatives — one produced
the corroboration finding, one produced a contradiction, but they were never
meant to be compared against each other. `fkl/tables.py::_column_groups`
catches this now: when a period label repeats in the primary header row, it
walks the rows above, forward-fills their spanning-cell labels, and folds each
group name into `ctx.scope` for the columns beneath it. The three duplicated
2023-24 cells now carry distinct scopes (`Urban`, `Rural`, `Combined`) and stop
being compared as alternatives.

**6. `fractile` was treated as a mere qualifier of the base quantity.** The
phrase "Expenditure fractiles: 0" from a page-margin percentile scale in the
RBI report produced a claim whose value was `0`, and the predicate gate said
"expenditure" and "expenditure fractile" were the same measurement adding a
qualifier. Three false contradictions followed. Distribution-shape words
(`fractile`, `percentile`, `quantile`, `decile`, `quartile`, `distribution`)
are now in `RATE_PREDICATE_TERMS` — a single extra word that names a
statistical operator replaces the property rather than qualifying it, exactly
the same as `deficit` or `growth`.

The effect on precision, same corpus, same six PDFs:

| | contradictions reported |
|---|---|
| before any of this | 0 (the entity gate blocked every candidate) |
| entity fix alone | 152, mostly false |
| \+ unit gate | 143 |
| \+ table-label guard | 33 |
| \+ predicate-gate fixes | 10 |
| \+ spanning-header fix | 3 |
| \+ fractile-as-distribution | **2** |

Both are real, both are the same finding at different periods, and none of the
false positives from the previous rounds survived.

### The pair the entity gate used to block is now surfaced — as a revision

The RBI's 3.5% inflation and the Economic Survey's 4.4% for the same year were
the motivating example for fixing entity detection. They now meet, and the
system classifies them `supersedes` rather than `contradiction`: the Survey
figure is stated as a projection, the RBI's as reported, and a revision is not
a disagreement. That is the better answer, and it was produced by a rule that
already existed and had never had a real pair to fire on.

### Lexical predicate matching cannot bridge institutional vocabularies

The IMF states `consumer prices - combined`, the RBI states `inflation`, the
Survey states `inflation rate`. The first shares no content word with the other
two, so it is never even a candidate. Acronym alignment handles `CPI inflation`
≡ `consumer price inflation`, but not `consumer prices` ≡ `inflation`, which
needs meaning rather than spelling.

This is the clearest case where the optional LLM would earn its place — except
that the current design escalates only pairs the rules marked ambiguous, and
these never become pairs at all. **Next step:** an optional semantic
candidate-generation channel (local embeddings over predicates only, which
measured well: 0.62–0.85 for true synonym pairs against ≤0.334 for false ones)
that proposes *additional* candidates while the deterministic rules still decide
every verdict.

### `partial_cover` and `component_of_total` share the output

The single `partial_cover` bucket used to dominate at 13,380 of 16,754
relationships. It has now split in two: **1,599 pairs land in
`component_of_total`** (a plausible narrower-vs-broader share) and 11,848 stay
in `partial_cover` (related properties, but the ratio is too small to call).
The `component_of_total` label is per-pair; a corpus-wide post-pass then groups
these by broader claim and confirms **33 decompositions** where the siblings
actually sum to the broader value within 5 %. Confirmed groups get their
reasoning trace extended with the arithmetic. **Next step:** promote confirmed
components to their own verdict kind (`component_confirmed`) and treat
component/broader pairs as first-class citizens in the UI so a reader can see
the whole decomposition at once.

### Entity detection is correct on five of six documents

Correct: `India` (IMF, RBI, Economic Survey), `Delhivery Limited` (Q4 deck),
`Delhivery` (annual report). Wrong: the prospectus elects `Equity Shares`.

That last one will not yield to the same treatment. In the 25 sampled pages the
issuer's own name appears **four times** — once as "DELHIVERY LIMITED" on the
cover, three times inside subsidiary names — because a prospectus refers to its
issuer as "our Company" throughout. "Equity Shares" appears 24 times and is
genuinely what the document keeps talking about. No frequency-based method
finds Delhivery here, and the definite-article rule does not fire (`Equity
Shares` takes an article only 29% of the time).

I tried two fixes and reverted both rather than keep a change I could not
justify:

- **Page-1 title block.** Taking the largest text on the first page fixes the
  prospectus (`DELHIVERY LIMITED`) and the IMF report (`INDIA`), but breaks the
  Delhivery annual report — whose cover reads "From India, For India." — and
  the Q4 deck, which is addressed to `BSE Limited`. Two fixed, two broken, on
  excerpted PDFs where page 1 is as often a contents page as a cover.
- **Admitting line-initial organisation names.** Exempting phrases that end in
  a legal suffix from the mid-sentence test did not fix the prospectus (the one
  all-caps mention is still a single occurrence) and it admitted `The Reserve
  Bank`, `Our Company` and `The Board` as entities.

**Next step:** a defining-appositive rule. A prospectus names its issuer once,
explicitly — `Delhivery Limited ... (our "Company")` — and a definition like
that is a stronger signal than any amount of frequency.

### Repeated column groups make one row label mean several things

The RBI's Appendix Table 4 puts two column groups under the same three year
headers, so the row `Credit-Deposit Ratio` has six cells and three of them are
labelled "2023-24". The table reconstruction captures the year header but not
the group above it, so all three become claims about the same period with
different values.

The visible consequence is in the exported cases: the same two rows produce a
`corroboration` (76.4 vs 75.8) *and* a `contradiction` (72.9 vs 75.8),
depending on which cell was compared. Both verdicts follow correctly from the
claims they were given; the claims are what is wrong. **Next step:** detect
spanning header cells and fold the group label into the column's context, which
would give these cells distinct scopes and stop them being compared as
alternatives.

### Two-column documents extract poorly

Tested against an academic paper (a two-column ACM article) the sentence rules
produce garbled predicates — "ing to the following criteria", "find th" —
because PyMuPDF's reading order interleaves the columns and hyphenation splits
across them. Tables are recovered correctly now that they are found as bands,
but prose is not. **Next step:** order text by column before sentence
segmentation, using the same vertical-gutter detection the table finder
already has.

### Other known gaps

- **No OCR.** Scanned or image-only PDFs yield nothing. The architecture has a
  place for it (an optional fallback when a page has no native text); it is not
  implemented.
- **Percentages without a stated denominator** are marked `underspecified`
  rather than compared. That is deliberate — `revenue = 33%` and
  `revenue = 7.46%` are proportions of different bases — but it also skips
  genuine share-vs-share comparisons.
- **Sentence recall is lower than table recall.** 4,131 of 4,773 claims come
  from tables. Prose-heavy documents give up fewer claims because the sentence
  rules need a label-linking-phrase-value pattern that much real writing does
  not follow ("Following economic growth of 6.5 percent…", "down from 9.8
  percent"). **Next step:** attach a value to the nearest preceding noun phrase
  rather than requiring a specific verb, and handle comparative constructions
  that carry two claims at once.
- **Predicate quality varies.** Table row labels are clean; sentence labels
  still occasionally carry a trailing fragment.
- **Relationships are cross-document only** by default. Intra-document
  contradictions (a director active on page 5, resigned on page 90) are not
  surfaced, though the machinery supports it.
- **No aggregation reasoning.** The system cannot check that segments sum to a
  stated total.
- **The LLM comparison is small.** The three-mode head-to-head covers 8 pages
  of one document, because a corpus-wide LLM run exhausts the free tier's
  8,000 tokens/minute without finishing. On that subset the LLM extracts more
  claims than the rules (44 vs 13) and takes 150x longer; whether that holds at
  corpus scale is untested on this account. The full-corpus comparison against
  the earlier LLM pipeline rests on measurements taken while that pipeline was
  the live implementation.

### Frontend

No build step and no bundler. `index.html` pulls React and `htm` from a CDN as
native ES modules, so `htm` tagged templates give JSX's semantics without a
compile step and an edit is visible on reload. Tailwind's play CDN carries the
design tokens — one surface ramp, one accent, one verdict palette — declared
once in the page head.

```
fkl/web/
  index.html            design tokens and import map; no application markup
  js/
    main.js             mounts the app
    App.js              sidebar shell, view switching, window-wide file drop
    lib/
      api.js            the only module that knows endpoint paths
      hooks.js          fetch and poll hooks (useAsync, usePoll, useStats, ...)
      format.js         verdict labels and tones, scores, context fields
      html.js           htm bound to React.createElement
    components/
      Sidebar.js        the app's only chrome: nav, counts, pipeline status
      ClaimList.js      one row per claim; used by Claims and Needs review
      RelationCard.js   one verdict, as an aligned two-column comparison
      Dropzone.js       upload target and the shared drop plumbing
      JobCard.js        staged ingest progress
      PageHead.js       page title and the corpus stat row
      Footer.js
    views/              Documents, Relations, Claims, Review
```

Three decisions worth naming. **A relation is a comparison, not two
paragraphs**: `RelationCard` puts both claims in one grid — value, then a row
per context field — and bands the rows that disagree, so what differs is
visible before anything is read. **Lists, not cards, for anything that
repeats**: Claims and Needs review can hold thousands of rows, so a row is one
line with the evidence, scores and source page one click away; a card per
claim fitted two facts on a screen. **Progress does not lie**: the ingest bar
fills for real where the pipeline reports counts (pages extracted, claims
grounded, pairs compared) and holds position under a moving stripe where it
cannot, rather than inventing a percentage.

### On not hard-coding

There is no reference anywhere in `fkl/` to a company, a document, a filename,
a page number, or a metric name. The rules key off document structure
(headings, tables, captions, page furniture) and general English patterns. The
one place a word list exists is `fkl/lexicon.py`, which is deliberately
separated so it can be reviewed for exactly this.

Both starter corpora — a logistics company's filings and three institutional
macroeconomics reports — run through the identical code path, and a test
asserts the macro corpus works without corpus-specific rules.

### Credentials

No credentials are in the repository. `.env` is gitignored, and the system's
default configuration needs none. The four required cases are committed under
[`samples/REQUIRED_CASES.md`](samples/REQUIRED_CASES.md) with their evidence,
so the results can be read without running anything. The full claim and
relation dumps are not committed — `scripts/export_samples.py` regenerates
them from a local run.

### Git history

The commit history follows the actual development sequence, including the
architectural change: extraction pipeline → grounding → provider swap →
cross-document matching → API/UI → deterministic re-architecture → tests and
benchmark → entity/predicate precision work.

The last of those is the one worth reading. It starts from a corpus that
reported zero contradictions and ends at ten, and the commit message records
